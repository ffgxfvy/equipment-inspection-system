# 项目讲解：这东西到底是什么

> 这份文档写给「刚跑通项目、但还没完全理解自己做了什么」的人。
> 读完你应该能：说清这个系统在解决什么业务问题、讲明白每个文件负责什么、
> 给面试官画出一条完整的请求链路。

---

## 一、一句话讲清这个系统

**它是一个"设备巡检的电子台账"**。

原来工厂里的巡检流程是这样的：

```
纸质台账（设备信息记在本子上）→ 人工排巡检计划 → 拿着纸去现场抄表
→ 发现问题记在本子上 → 回到办公室录入 Excel → 忘了跟进异常 → 出事了才想起来
```

这个系统把这四步全部搬到线上：

| 原来的做法 | 系统里的模块 |
|---|---|
| 纸质台账 | **设备台账**：每台设备一张卡片，编号、位置、型号、巡检周期 |
| 人工排计划 | **巡检任务**：创建任务、分派给巡检员、状态流转（待执行→执行中→已完成） |
| 现场抄表 | **巡检记录**：提交温度/压力读数、拍照上传、判定正常或异常 |
| 忘了跟进 | **异常闭环**：异常自动把设备标成"故障"，处理完自动恢复"运行" |
| 事后翻本子 | **首页看板**：设备状态分布、近 7 天巡检趋势、待处理异常列表 |

**为什么这个选题对他有意义**：他本科做过「工业仪表擦拭的机械臂项目」，知道现场真正会产生什么数据。
所以数据模型里保留了 `last_temperature`、`last_pressure` 这两个采集字段——
纯软件背景的人容易忽略这一点。

## 二、你启动了两个东西，它们分别是什么

双击 `start-backend.bat` 和 `start-frontend.bat` 后，你的电脑上跑着**两个独立的程序**：

```
┌─────────────────────────────┐        ┌─────────────────────────────┐
│  前端进程（Node.js 跑的）      │        │  后端进程（Java 跑的）        │
│                             │        │                             │
│  start-frontend.bat         │        │  start-backend.bat          │
│  → Vite 开发服务器           │        │  → SpringBoot 内嵌 Tomcat   │
│                             │        │                             │
│  地址 http://localhost:5173  │        │  地址 http://localhost:8080  │
│                             │        │                             │
│  作用：把 .vue 文件实时编译成  │        │  作用：接收请求、查数据库、   │
│       浏览器能懂的 HTML/JS     │        │       返回 JSON 数据         │
│                             │        │                             │
│  它的产物"住在"浏览器里        │        │  它的产物就是 JSON 文本       │
└──────────────┬──────────────┘        └──────────────┬──────────────┘
               │                                      │
               │   浏览器里跑的其实是前端代码            │
               │                                      │
               └──────── /api/xxx 请求 ───────────────┘
                    （Vite 开发时自动把 /api 转发到 8080）
```

**为什么要有两个进程？**

这是现在最主流的做法：**前后端分离**。

- 后端只管"数据"——你给我请求，我给你 JSON。它不知道页面长什么样。
- 前端只管"界面"——它拿到 JSON，负责画成表格、图表、表单。
- 好处：后端可以同时服务网页、手机 App、小程序；前端改样式不用重启后端。
- 代价：要处理跨域问题（本项目在开发环境用 Vite 的代理解决，生产环境用 Nginx 反向代理）。

> **你打开 http://localhost:5173 看到的页面，是前端进程给的**。
> 页面上显示的设备列表数据，是前端再去找后端（8080）要的。
> 如果后端没启动，页面能打开但会提示"网络异常"。

## 三、后端内部：一层一层剥开

后端代码在 `backend/src/main/java/com/renjie/inspection/` 下，分了 7 个包。
一次请求会**从上往下穿过**这些层：

```
浏览器发来  GET /api/equipments?pageNum=1
      │
      ▼
┌──────────────────────────────────────────────────────┐
│ ① 拦截器层  security/                                 │
│    AuthInterceptor                                    │
│      · 从请求头取 Authorization: Bearer xxx           │
│      · 解析 JWT，失败直接返回 401（不往下走）           │
│      · 成功则把用户信息放进 UserContext（ThreadLocal） │
│    RoleInterceptor                                    │
│      · 看方法上有没有 @RequireRole("ADMIN")           │
│      · 角色不够就返回 403                              │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ ② 控制器层  controller/                                │
│    EquipmentController                                │
│      · @GetMapping("/equipments") 把 URL 映射到方法    │
│      · 参数校验（@Valid，校验规则写在 dto 的注解上）      │
│      · 调用 Service，把结果包进统一的 R<T> 结构返回      │
│      · 只做"翻译"，不写业务逻辑                         │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ ③ 业务层  service/                                     │
│    EquipmentService                                   │
│      · 组装查询条件（关键字模糊匹配、状态精确匹配…）      │
│      · 业务规则判断（编号不能重复、状态取值必须合法）      │
│      · 跨表联动（提交异常记录 → 改设备状态）             │
│      · @Transactional 保证多步操作要么全成功要么全回滚    │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ ④ 数据访问层  mapper/                                  │
│    EquipmentMapper extends BaseMapper<Equipment>      │
│      · 只是个接口，没有实现类！                          │
│      · 方法（selectPage / insert / updateById…）        │
│        是 MyBatis-Plus 在启动时动态生成的                │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ ⑤ 数据库  H2（内存）/ MySQL                            │
│    表：equipment / inspection_task / inspection_record │
└──────────────────────────────────────────────────────┘
```

**每一层的职责边界**（这是面试官很爱问的）：

| 层 | 只该做 | 不该做 |
|---|---|---|
| Controller | 接参、校验、调用 Service、包装响应 | 写 SQL、写业务判断 |
| Service | 业务规则、事务、编排多个 Mapper | 处理 HTTP 对象 |
| Mapper | 数据存取 | 业务判断 |

> **为什么这么分？** 因为"业务规则"和"访问方式"变化频率不同。
> 数据库从 MySQL 换成 Oracle，只动 Mapper；业务规则改了，只动 Service；
> 接口协议改了，只动 Controller。**变化点被隔离开了，改动就不会互相牵连。**

## 四、几个关键概念（都是你项目里实际用到的）

### SpringBoot 是什么

它是**帮你把"启动一个 Web 服务"这件事变简单**的框架。

不用 SpringBoot 的话，你要自己配 Tomcat、写 web.xml、手工 new 各种对象……
用 SpringBoot 之后，你只写一个 `InspectionApplication`：

```java
@SpringBootApplication
public class InspectionApplication {
    public static void main(String[] args) {
        SpringApplication.run(InspectionApplication.class, args);
    }
}
```

跑这一行，它自动做了：启动内嵌 Tomcat、扫描注解、创建对象、读配置文件、连数据库。

### IoC / 依赖注入（DI）

看 `InspectionTaskService` 的构造器：

```java
@Service
@RequiredArgsConstructor          // Lombok：自动生成带参构造器
public class InspectionTaskService {
    private final InspectionTaskMapper taskMapper;
    private final EquipmentMapper equipmentMapper;
}
```

**你从来没有写过 `new InspectionTaskMapper()`**，但 `taskMapper` 就是能用。

原因：Spring 启动时会扫描到 `@Service`、`@Mapper` 这些注解，**自己创建对象并保管起来**；
发现 `InspectionTaskService` 需要一个 Mapper，就把已经创建好的那个"塞"进来。

这就是 **IoC（控制反转）**——对象由容器创建，不由你创建；
**DI（依赖注入）**——依赖由容器塞进来。

**好处**：写测试的时候，你可以塞一个假的 Mapper 进去，不用真的连数据库。

### MyBatis-Plus 是什么

它是**帮你省掉写 SQL 的 ORM 框架**。

- 原生 MyBatis：每个查询都要写 XML 或注解里的 SQL
- MyBatis-Plus：`extends BaseMapper<Equipment>` 就白送你 `insert` / `selectById` / `updateById` / `deleteById`，
  分页、条件构造（`Wrappers.lambdaQuery()`）、逻辑删除也是自动的

```java
// 不用写一行 SQL，它自动生成成：
// SELECT * FROM equipment WHERE status = ? AND deleted = 0 ORDER BY update_time DESC
equipmentMapper.selectList(Wrappers.<Equipment>lambdaQuery()
        .eq(Equipment::getStatus, "RUNNING")
        .orderByDesc(Equipment::getUpdateTime));
```

> 注意 `deleted = 0` 是自动加的——这是实体上 `@TableLogic` 注解的效果（逻辑删除）。
> 删设备时它执行的是 `UPDATE ... SET deleted = 1`，数据还在库里，只是查不到了。

### JWT 是什么

**一种"无状态"的登录凭证。**

传统 Session 的做法：登录成功后服务端存一份记录，给浏览器一个 sessionId；
下次请求带着 sessionId，服务端去查这份记录。**服务端要存东西**，多台服务器还要共享。

JWT 的做法：登录成功后服务端**签发一个字符串**，里面用 Base64 装着"用户1 / admin / ADMIN 角色"，
并用密钥签名。下次请求带上它，服务端**只要验证签名就能确认身份，不用查任何存储**。

```
eyJhbGciOiJIUzUxMiJ9 . eyJzdWIiOiIxIiwidXNlcm5hbWUiOiJhZG1pbiJ9 . 签名
       头部                    载荷（可被任何人解开看）              签名（没法伪造）
```

**两条重要认知**（面试常问）：
1. **载荷只是 Base64，不是加密**——所以绝不能往里放密码、身份证号；
2. **服务端没法主动让 token 失效**——用户改密码后旧 token 依然有效，要解决得加 Redis 黑名单。

### H2 是什么，为什么要用它

H2 是一个**纯 Java 写的数据库，可以跑在内存里**。

你启动后端时，它在 JVM 内存里建了库、执行 `schema-h2.sql` 建表、执行 `data-h2.sql` 灌演示数据。
**所以你不用装 MySQL 就能看到完整效果，重启后数据恢复到初始状态。**

`application-prod.yml` 里配的是真正的 MySQL，用 `--spring.profiles.active=prod` 切换。

**这不只是为了方便**——它降低的是"别人跑通你这个项目"的成本。招聘方 clone 下来一条命令就能看到效果，
这个体验差别很大。

## 五、跟着一次真实请求走一遍

### 场景 1：登录

```
① 浏览器  POST /api/auth/login
          body: {"username":"admin","password":"admin123"}
              │
              ▼
② AuthInterceptor  发现路径是 /auth/login（在白名单里）→ 放行
              │
              ▼
③ AuthController.login(@Valid @RequestBody LoginRequest)
   · @RequestBody 把 JSON 转成 Java 对象
   · @Valid 校验：用户名密码非空（规则在 LoginRequest 的注解上）
              │
              ▼
④ AuthService.login()
   · userMapper.selectOne(...)  查库，拿到 SysUser（含 BCrypt 密码哈希）
   · BCryptPasswordEncoder.matches(明文, 哈希)  校验密码
   · 密码错 → throw BizException(401)
   · jwtUtil.generate(userId, username, role)  签发 token
              │
              ▼
⑤ 返回 R.ok(new LoginResponse(token, ...))
   实际响应：{"code":200,"message":"登录成功","data":{"token":"...","role":"ADMIN"}}
```

### 场景 2：提交巡检记录（业务最复杂的一条）

```
前端  POST /api/records
      {"equipmentId":13,"result":"ABNORMAL","abnormalDesc":"读数异常",...}
              │
              ▼
InspectionRecordService.submit()   ← 方法上标了 @Transactional
   │
   ├─ ① 校验设备存在
   ├─ ② 跨字段校验：结论异常 → 必须填异常描述，否则 throw BizException(400)
   │
   ├─ ③ 插入 inspection_record            （一条新记录）
   │
   ├─ ④ 更新 equipment                    （联动 1）
   │      last_inspect_time = 巡检时间
   │      next_inspect_time = 巡检时间 + 巡检周期
   │      last_temperature  = 实测温度
   │      status            = FAULT（因为结论异常）
   │
   └─ ⑤ 更新 inspection_task              （联动 2）
          status = DONE，finish_time = 巡检时间
   
   以上 ③④⑤ 在**同一个事务**里：
   任何一步失败，前面已执行的步骤全部回滚，数据库不会出现"记录存了但设备状态没改"的中间态。
              │
              ▼
返回 {"code":200,"data":{...记录详情...}}
```

> **为什么这里必须用事务？** 因为"提交记录"和"改设备状态"是**业务上不可分割的一步**。
> 如果只成功了一半，出现的就是"巡检员说设备坏了，但系统里设备还是正常运行"——
> 这种数据不一致比报错更难排查。

## 六、数据库四张表的关系

```
                ┌──────────────────┐
                │    sys_user      │  用户（管理员 / 巡检员）
                │  id, username    │
                │  password(BCrypt)│
                │  role            │
                └────────┬─────────┘
                         │ inspector_id
                         │
   ┌─────────────────────┴──────────────────────┐
   │                                            │
   ▼                                            ▼
┌──────────────────┐   equipment_id   ┌──────────────────────┐
│ inspection_task  │─────────────────►│     equipment        │
│ 任务              │                  │  设备台账              │
│  task_no         │                  │   code（唯一）         │
│  status 状态机    │                  │   status              │
│  priority        │                  │   inspect_cycle_days  │
│  plan/finish_time│                  │   last/next_inspect…  │
└────────┬─────────┘                  │   last_temperature    │
         │ task_id                    │   last_pressure       │
         │                            └───────────▲──────────┘
         ▼                                        │ equipment_id
┌──────────────────────────────────────────────┐  │
│           inspection_record                   │  │
│  巡检记录                                      │  │
│   result（NORMAL / ABNORMAL）──────────────────┘
│   abnormal_desc, handle_status, photo_url
│   temperature, pressure
└──────────────────────────────────────────────┘
```

**四个字段要记住**（面试讲数据模型时会用到）：

| 字段 | 作用 |
|---|---|
| `deleted` | 逻辑删除标记。所有查询自动带 `deleted = 0`，删除只是置 1 |
| `create_time` / `update_time` | 审计字段，由 `MyMetaObjectHandler` 自动填充，不靠人记得写 |
| `equipment.last_temperature` / `last_pressure` | 为对接现场采集预留的字段，巡检时回写 |
| `equipment.next_inspect_time` | 由"任务完成"或"提交记录"驱动计算，**不接受前端直接传** |

最后那条是个刻意的设计：**凡是系统能算出来的字段，就不让前端传**。
否则前端传个乱七八糟的值进来，数据的可信度就没了。

## 七、前端那边是什么

前端在 `frontend/src/`：

| 目录/文件 | 作用 |
|---|---|
| `main.js` | 入口：创建 Vue 应用，挂上路由和 Pinia，全量注册 Element Plus 图标 |
| `App.vue` | 根组件，只有一行 `<router-view />` |
| `router/index.js` | 路由表 + **登录守卫**（没登录一律踢回 /login） |
| `store/user.js` | 登录状态（Pinia）。token 存 localStorage，刷新页面不用重新登录 |
| `utils/request.js` | **Axios 封装**：自动带 token、统一处理业务码、401 自动跳登录页 |
| `api/*.js` | 按模块拆的接口定义，页面里不直接写 URL |
| `layout/index.vue` | 侧边栏 + 顶栏的骨架 |
| `views/*.vue` | 5 个页面：登录 / 看板 / 台账 / 任务 / 记录 |
| `components/RecordFormDialog.vue` | 提交巡检记录的弹窗（含照片上传） |

**`utils/request.js` 是前端的核心**，它做了三件事：

```js
① 请求拦截器：每个请求自动加上 Authorization: Bearer <token>
② 响应拦截器：code === 200 才把 data 交给页面，否则统一弹提示
③ 401 时：清掉登录态并跳回登录页
```

**所以页面代码里看不到任何 try/catch 和"如果失败就提示"的重复代码**——
`const data = await pageEquipments(query)` 拿到的就是纯数据，出错了会被拦截器统一处理。

> 这也是我之前修那个 bug 的原因：如果 HTTP 返回 4xx，Axios 会走 error 分支而不是正常分支，
> 服务端写的校验提示就到不了界面。所以我把后端改成 HTTP 恒为 200、业务码放 body。

## 八、面试时怎么讲（三段式）

### 第一段：业务是什么（30 秒）

> 我做的是一个工业设备巡检管理系统。起因是我本科做过工业仪表维护的机械臂项目，跑真机时
> 发现巡检的痛点更多在管理侧——台账散在 Excel、记录靠纸质表格、异常跟进靠人记。
> 所以我用 SpringBoot + Vue 把这条流程做成了系统：设备台账、巡检任务、巡检记录、
> 异常闭环，加上一个统计看板。

### 第二段：技术上怎么做（2 分钟）

> 后端是 SpringBoot 3 加 MyBatis-Plus，分了 Controller / Service / Mapper 三层，
> 4 张业务表；认证用 JWT 无状态方案，密码用 BCrypt 哈希；鉴权用自定义拦截器加
> `@RequireRole` 注解，比引整套 Spring Security 更轻、链路也更好讲清楚。
> 前端是 Vue 3 加 Element Plus，用 Axios 拦截器统一处理 token 和错误，看板用 ECharts。
> 另外配了 H2 内存库的 dev 环境，clone 下来不用装数据库就能跑；
> 写了 Dockerfile 多阶段构建和 docker-compose 三容器编排。

### 第三段：亮点和踩坑（1 分钟）

选一个讲，推荐这两个：

> **联动与事务**：提交一条异常巡检记录时，要同时插入记录、把设备状态改成故障、
> 把关联任务置为已完成。这三步跨三张表，任何一步失败都会造成数据不一致，
> 所以我用 `@Transactional` 包住，并把跨字段校验（结论异常必须填描述）放在事务入口，
> 尽早失败避免无谓的写操作。

> **N+1 优化**：任务列表要显示设备名和巡检员名。一开始我逐条去查关联表，
> 14 条数据就要 29 次 SQL。后来改成查出主表后用 `selectBatchIds` 批量查关联表、
> 在内存里用 Map 拼装，降到 3 次。

## 八点五、Excel 导入为什么是「部分成功」

面试如果问到"你怎么设计导入功能"，可以这么讲：

> 导入一份 200 行的表，如果第 37 行格式不对，有两种做法：
>
> **全量事务**——整批回滚。用户改完第 37 行再导一次，如果第 89 行也错了，
> 又要来一轮。200 行可能要试十几次。
>
> **逐行独立**——能导的先导进去，返回"成功 197 行，失败 3 行，第 37/89/152 行分别是……"，
> 用户改这三行单独再导即可。
>
> 我选了后者。代价是数据库里已经写进去一部分，所以接口**必须返回明确的成功/失败统计**，
> 不能让调用方以为整批都成功了。

另外三个细节：

- **按表头名读列，不按列序号**。按序号读时，用户删掉"备注"列会导致"安装位置"被读进
  "类目"里——不报错，只是数据全错，这是最难排查的一类问题。
- **逐行调用 `EquipmentService.create()`**，而不是自己拼 insert。
  这样导入和手工新增走同一套校验，不会出现"页面上不允许的编号，导入却能成功"。
- **编号重复只报错不覆盖**。覆盖会静默改掉现场已有数据，风险远大于收益。
